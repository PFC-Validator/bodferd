Bodferð
secure node communications

A secure way for a node operator to send a signed message and an encrypted file to THORChain maintainers over Tor.

The operator registers a dedicated communication key, encrypts each report locally to a verified maintainer recipient, and sends opaque ciphertext through an isolated relay. The maintainer verifies the original signatures and decrypts the report in their own environment.

This is a design document. The CLI and service are not implemented. The reading website is separate from the future Tor-only relay.

Two channels, one chain of trust

Public enrollment establishes who may sign. Confidential transport delivers reports without giving the relay a decryption key. These channels have different privacy boundaries.

Tor conceals connection location; the node signature identifies the sender to the admission relay. Static age recipient keys do not provide forward secrecy. These are explicit limits, not implementation defects to hide.

Register two keys, not one

An age recipient is for encryption. Future message signatures use a separate Ed25519 communication key. The registration binds both keys to the node, service, environment, expiry and permitted actions.

  1. Create keys locally. Keep the communication signing key and reply age identity on the operator’s machine.
  2. Prepare a scoped registration. Include both public keys, node authority, a one-use challenge, key epoch and expiry.
  3. Announce its digest with make relay. Only the public registration digest goes to Discord.
  4. Verify authority and possession. Check the authorizer against independent chain state and prove control of both newly registered keys.
THOR-RELAY-REGISTER-V1 sha256=<registration-digest>

THORChain’s existing release instructions already describe publishing an age public key through make relay to receive encrypted patches. The existing command signs and broadcasts; it is never the confidential report transport. Read the official release procedure.

Two evidence paths, clearly labeled

Original node signature · preferred
Import the original signed relay envelope, when available, or use a separate sign-only adapter. Verify the actual signature and chain authority independently.
Registrar-witnessed · additional trust
When only the unmodified Discord announcement is available, designated registrars verify it and issue policy-authorized attestations. Production proposes two independent witnesses. Screenshots and usernames are insufficient.

Maintainer keys need an independent role-authorizing policy. A node signature can establish node authority; it cannot appoint its signer as a THORChain maintainer.

From local file to verified report

  1. Verify the recipient policy. Reject substituted, expired or rolled-back keys before encrypting anything.
  2. Package and sign the content. Include the message, file, filenames and an inner signed manifest. Encrypt the package locally with age.
  3. Sign admission context. Bind the ciphertext hash and size to the service, recipient policy, environment, registration, challenge and submission ID.
  4. Upload over Tor. The relay verifies authorization and quotas before accepting a bounded body. Atomic durable state prevents replay from creating duplicate accepted jobs.
  5. Forward an encrypted email bundle. Original evidence and ciphertext are wrapped in another age envelope so the mail provider cannot read the node signature.
  6. Verify at the maintainer. Decrypt into staging, check both signatures and all file hashes, then present the report. Never automatically open or execute attachments.
Admission is not decryption verification. An opaque relay can validate authorization, exact bytes and bounded age structure. Only the maintainer can establish that the report decrypts successfully.

Receipt states distinguish acceptance, queueing, SMTP acceptance, failure and a maintainer-signed acknowledgement. The operator retrieves acknowledgements and encrypted replies through a private Tor polling capability.

Security controls built into the design

The protocol incorporates all ten findings from the initial review. Each control has an observable acceptance check in the full reference.

  • Honest encryption claims: the maintainer verifies decryptability; the relay never claims to have decrypted.
  • Independent recipient trust: signed policy, pinned authority, expiry and rollback rejection.
  • Scoped delegation: separate communication keys, short validity, fresh authority checks and durable revocation.
  • Exact signature binding: inner content authorship plus outer ciphertext and destination context.
  • Durable replay protection: one-use challenges, atomic outbox insertion and idempotent retries.
  • Defined operator eligibility: exact node/operator authority; unrelated bond providers excluded.
  • Tor-only submission: pinned onion, local SOCKS, no redirect or direct fallback.
  • Metadata minimization: encrypted filenames and sender proofs, generic email, bounded retention.
  • Abuse and file defenses: admission before upload capacity, parent quotas, global caps and staged verification.
  • Delivery and environment separation: fixed routes, distinct keys and signed end-to-end acknowledgement.

A valid node signature does not establish that the report is true, the operator is uncompromised, or the attachment is safe. The relay can still suppress delivery. A compromised plaintext endpoint can still expose a report.

From reports to trusted conversations

Bodferd can grow into secure communication between node operators, THORNode developers and trusted groups. Its distinct job is to verify identities and authorize membership. Conversation encryption and device sessions should come from an established messaging system.

First evaluate an existing messenger with a small identity adapter. A reviewed MLS implementation is an alternative for group key management, subject to a separate design and security review. Static age recipients remain appropriate for the first reporting workflow.

  • Node authority, developer roles and group administration have separate sources of trust.
  • Every device needs explicit authorization; membership changes update conversation keys.
  • Removed members retain what they previously received. Future-message access ends after the removal takes effect.
  • All messaging traffic needs demonstrated Tor support, including background key fetches and notifications.

V1 provides reports and bounded encrypted replies. Group chat is a future direction with its own protocol, verification requirements and explicit permissions. The full design now compares stock Signal integration with a client using libsignal, and specifies how device-bound role credentials govern membership without changing the ratchet.

What must be settled before implementation

The protocol boundaries are specified. These prerequisites need real evidence before the service can be enabled.

  • Confirm maintainer and registrar identities, policy-authority fingerprints and threshold.
  • Test node/wallet sign-only compatibility and access to original signed relay envelopes.
  • Establish independent current and historical chain-state verification.
  • Provision dedicated onion identities and separate test/production configuration.
  • Verify mail-provider TLS and attachment limits, then validate pilot resource and retention defaults.
  • Produce interoperable protocol fixtures and obtain independent cryptographic/parser review.

The first deployment uses synthetic data and the test recipient. Production starts only after the required controls have verification evidence.

A standalone project

PFC-Validator/bodferd is the standalone repository. It owns its trust policy, key lifecycle, storage and deployment. The relay has dedicated credentials and an onion-only admission boundary.
